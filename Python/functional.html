Functional Programming

Functions are the first-class objects, which means you can do anything with a function that can be done with “data”. This shifts the programming focus to “what” is to be computed rather than “how” is it to be computed. As a first-class object, functions can be - passed as arguments to other functions, - returned from functions, - stored in variables and data structures and - built at run time.

It allows many functional programming design patterns such as:

  • Curry/ Partial function application - Creating new functions by holding a parameter constant
  • Closure - Return functions from functions
  • Pure Functions: separate pure code from impure code.
  • Function composition
  • Composable functions
  • High Order Functions
  • MapReduce Algorithms - Split computation in multiple computers cores.
  • Lazy Evaluation ( aka Delayed evaluation)
  • Pattern Matching
  • Monads
# Functions can be passed as a function and returned as a function
def derivate (f, dx=1e-5):
    def _(x):
        return (f(x+dx) - f(x))/dx
    return _

def f(x): return x**2 - 2*x + 3

# function stored as a variable, similarly can be stored in a list or dictionary
df = derivate(f)   # 2x - 2

df(1), df(2), df(3), df(5)  # 0, 2, 4,

Pure Functions

A pure function is a function which returns identical values without any side effects. For same input, the function always returns the same output being fully determined by only its arguments and not relying on any global variables or internal state, also the data passed remains unchanged. (i.e no variation with local static variables, non-local variables, mutable reference arguments or input statements). Hence, pure functions are stateless and deterministic (predictable) eg. mathematical functions. This allows the functions to be easily chained or composed together, ran in parallel, multi-thread, multi-core, GPU and distributed systems and also easier to debug and test. Whereas impure functions generally maintain a hidden state or access some global variables, and doesn’t always have the same output for the same input. eg: functions used for IO (print, write file,…)

We can try different strategy to purify a function, - pass the external variable to the function. - If functions modifies a list, create a copy of the list and modify the copy and return the copy instead.

def min(x, y): return x if (x < y) else y  # pure function

z = min(5,4)

def myMul(x): return z*x   # impure, depends on z for computation
def pureMul(x,z): return z*x  # purifying myMul

myMul(3)
12

Absence of side-effects in pure functions allows Referential Transparency, which means that any sub-expression can be replaced by its value within an expression at any time without changing the evaluation of the whole expression. It can be basically stated as “replace equals by equals”. This allows program transformation, manipulation and equational reasoning. This allows computations to be safely distributed over multiple processors/threads. Furthermore, previously evaluated expressions can be memoized.

Functions utilizing global variables may violated referential transparency (aka referential opacity), eg: counters, random number generators. rand() + rand() != 2 * rand()

def square (x): return x * x

square (3) + square (3) == 2 * square (3)  # Referential transparency

# Referential opacity due to global state side-effects
state =  1

def counter():
  global state
  state += 1
  return state

counter() + counter() == 2 * counter() 
False

Closure

Closure is a function that remembers the environment at which it was created, and access variables in that scope (i.e lexically scoped name binding)

def make_adder(x):
    def adder(y):
        return x + y
    return adder

add5 = make_adder(5)
add5(4)
9
# Mutable state with closure
idx = 100 
 
def make_counter():
    idx = -1    
    def _():
        nonlocal idx
        idx = idx + 1
        return idx    
    return _

counter1 = make_counter()
print(counter1(), counter1())
del make_counter
counter1()
0 1

Currying and Partial Applications

Currying is the decomposition of a function of multiples arguments in a chained sequence of functions of a single argument. The name currying comes from the mathematician Haskell Curry who developed the concept of curried functions. Curried functions can take one argument at a time and a uncurried function must have all arguments passed at once.

A function of multiple arguments is converted into a new function that takes fewer arguments, some arguments are supplied and returns function with signature consisting of remaining arguments. Partially applied functions must not be confused with currying.

def f(x, y, z): return 10*x - 2*y - z  # uncurried

curried_f = lambda x: lambda y: lambda z: 10*x - 3*y -z

f(3,4, 5) == curried_f(3)(4)(5)

partial_f = curried_f(1)(1)

partial_f(5)

Higher-Order Functions or functionals or operators

Higher-order function are functions that takes a function as an argument and/or return a function as a result. All other functions are called first-order functions.

map, filter and reduce (fold left) are ubiquitous higher-order functions - map :applies a function to each element of a sequence: list, vector, hash map or dictionary and trees. -

# Map
list(map(math.sqrt, [4, 9, 16]))  # list function of map operates through recursion, Python doesn't have TCO hence avoid recursion

[math.sqrt(x) for x in [4,9,16] ]  # strict map

# native map is faster as it is implemented in C
def lazy_map (f, xs): 
    for x in xs:
        yield f(x)

g = lazy_map (math.sqrt, [1, 4, 9])
next(g), next(g)
(1.0, 2.0)

Recursion

Tail Call Optimization and Tail Recursive Functions

A tail call is a function call which is the last action performed by a function.

Tail Call Optimization (TCO) or tail call elimination (TCE) or tail recursion elimination (TRE) replaces tail calls with jumps that guarantess that loops implemented using recursion are executed in constant stack space. Schinz M. and Odersky M. - 2001. Without tail call optimization each recursive call creates a new stack frame by growing the execution stack. Eventually the stack runs out of space and the program has to stop. To support iteration by recursion functional languages need tail call optimization. Schwaighofer A. 2009.

Python doesn’t have TCO Support. To perform recursion safely a language must support TCO - Tail Call Optimization. Even if there is TCO support a non tail recursive function can lead to an unexpected stack overflow. Recursion allow greater expressiveness and many algorithms are better expressed with recursion. Recursion must be replaced by loops constructs in languages that doesn’t support TCO.
